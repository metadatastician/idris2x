*One command, exactly the compiler you pinned, or a loud error that tells you how to fix it.*

idris2x materializes an exact Idris 2 + Chez Scheme toolchain from a lockfile and runs it. It downloads an immutable,
signed, self-testing *capsule*, verifies it, unpacks it atomically into a content-addressed cache, runs canaries, and execs
the real compiler. It needs no system Chez, no `sudo`, no Nix and no mise. It works offline and air-gapped, and it is
designed so that existing pins keep working even if this project is abandoned.

[IMPORTANT]
====
*Status: Phase 0 complete, Phase 1 in progress.* The design is pinned in nine ADRs (0004–0012, two still proposed) and was tested on real builds:
126 chaos checks pass against both the prototype launcher (bash) and the Rust launcher, and 11 of 12 canaries pass, on a real Linux x86_64 capsule.
The Rust launcher is partly merged and unreleased; the capsule factory CI and published capsules do *not* exist yet. Nothing below the "Planned" line
is usable today. Unofficial; not affiliated with the Idris 2 or Chez Scheme projects.
====

== Why

Installing Idris 2 today means building it from source against whichever Chez Scheme your system happens to have
(pack, distro packages, Homebrew), and the compiler bakes absolute paths into everything it produces. idris2x treats a
compiler toolchain as an *artifact with a digest*, not a package: the same lockfile gives the same compiler on a laptop,
in CI, on a server and in an air-gapped lab, years apart.

== Five invariants

[cols="1,2,4",options="header"]
|===
| ID | Invariant | Meaning
| I1 | No silent drift | What executes is exactly the pinned digest, or nothing.
| I2 | Atomic or absent | The store never contains half-state. Interrupted installs are garbage by definition.
| I3 | Loud by default | Every failure is a typed error with a stable ID, an exit code, a runbook and the exact fix command.
| I4 | The past never breaks | Old digests run under new launchers. A lockfile plus capsule bytes is sufficient forever.
| I5 | Verify before trust | Signature, digest and probes before first execution.
|===

== Planned usage (Phase 1)

[source,bash]
----
idris2x init                          # scaffold idris2x.toml
idris2x pin 0.8.0                     # verify the signed channel, write idris2x.lock
idris2x exec --locked -- idris2 --check src/Proof.idr
idris2x doctor --json                 # fingerprint, probes, exact fix commands
idris2x fetch -o bundle.tar.gz        # air-gap prefetch; then: idris2x install --from bundle.tar.gz
idris2x gc --keep-last 3              # reclaim the store
----

Today the same surface exists as a tested prototype for Linux: link:scripts/proto/[`scripts/proto/idris2x.sh`].

== What Phase 0 established

* Upstream ships no Linux or macOS binaries of either project, so capsules are built from pinned sources: Chez 10.4.1 in 164 s, Idris 2 v0.8.0 in 604 s on four cores.
* Relocation works without patching: Chez 10 finds its boot files relative to the executable, and Idris 2 honours `IDRIS2_PREFIX` at runtime. The launcher execs `scheme --program idris2.so` directly with an environment it *resets* (link:docs/decisions/0005-relocation-by-direct-exec.adoc[ADR 0005]).
* A Linux x86_64 capsule is 137 MB unpacked and 35 MB gzip; a cold install from a mirror takes 3.3 s.
* Nine assumptions of the original plan were refuted or corrected with primary sources; the launcher is Rust, per the estate language policy (link:docs/decisions/0011-estate-compliance-mint-rust-cli.adoc[ADR 0011]).

Full evidence: link:docs/status/PHASE0-REPORT.adoc[Phase 0 report].

== Governance badges

The *K9 conformance* badge in the row at the top becomes live after
`just repo-init` replaces the owner and repository placeholders in its URL,
GitHub Pages is enabled with source "GitHub Actions", and an eligible push to
`main` publishes it. `.github/workflows/dogfood-gate.yml` stages it and
`.github/workflows/pages.yml` deploys it with the repository's GitHub Pages
site; it is read back through the shields endpoint.

[cols="1,3",options="header"]
|===
| Badge | What it means

| green `success`
| The K9 lane ran for that commit on `main` and passed.

| red `failure`
| The K9 lane ran for that commit on `main` and failed.

| grey `skipped`, `cancelled`, `unavailable`, `unknown`
| That commit produced *no trustworthy* K9 result. Grey is not "pending" and
  not a stale green: a skipped, cancelled or unavailable lane replaces an
  earlier green badge with grey.
|===

* The badge is *generated output*, served from the Pages site. It is not written
  to a branch because the estate's branch ruleset requires a pull request for
  every branch write; a Pages deployment is not one.
* Nothing in the badge pipeline can turn a failing validation green: only a
  lane that ran and passed, with its artifact present, renders brightgreen.

The full operational contract - the exact state table, how API errors are
classified, how concurrent publications are serialised, and how to repair a bad
file - is in link:.github/workflows/README.adoc[`.github/workflows/README.adoc`].
